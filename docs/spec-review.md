## 一、总体评价

### 1.1 优点

| 维度 | 评价 |
|------|------|
| **问题定义** | 目标用户（开发团队）与价值主张（自动化重复任务）表述清楚 |
| **功能结构** | FR-1～FR-8 分层合理，覆盖编辑器、引擎、协作、模板、监控等主链路 |
| **验收标准** | 采用 Given/When/Then，且区分 human-judgment / programmatic，便于测试对齐 |
| **技术约束** | 技术栈与容量上限已给出，有利于架构早期评估 |

### 1.2 主要风险（需优先处理）

| # | 风险 | 影响 |
|---|------|------|
| R1 | **范围自相矛盾**：非目标写「单体、非分布式」，NFR 与约束又写「高并发、分布式扩展」 | 研发与采购预期不一致，工期难估 |
| R2 | **MVP 未定义**：一期要交付哪些 FR/节点，文档未区分 P0/P1/P2 | 易做成「缩小版 n8n」，首期无法上线 |
| R3 | **竞品差异化弱**：与 n8n 对比仅一句「本地模型、节点扩展」，无用户场景与放弃清单 | 难以说服立项与资源投入 |
| R4 | **安全与合规缺口**：命令执行、SSH、文件读写、代码节点无沙箱与审计说明 | 企业客户无法采纳 |
| R5 | **开放问题悬而未决**：暂停/恢复、批量操作等直接影响引擎设计 | 架构返工风险高 |

### 1.3 评审评分（5 分制）

| 维度 | 得分 | 说明 |
|------|------|------|
| 问题与价值 | 3.5 | 有目标用户，缺量化收益与典型场景 |
| 范围与优先级 | 2.5 | 功能全但无 MVP、无版本路线图 |
| 可验收性 | 3.5 | AC 有结构，但覆盖不全、部分不可测 |
| 一致性 | 2.0 | 非目标 / NFR / 约束多处冲突 |
| 安全与合规 | 2.0 | 高风险能力未约束 |
| 商业与运营 | 2.5 | 模板市场、多租户、计费均未涉及 |
| **综合** | **2.9** | 建议修订 v1.1 后再评审 |

## 二、分章节评审意见

### 2.1 概述 / 核心目标 / 非目标

**结论**：基础信息完整，需补强「为什么不用 n8n」与「首期交付边界」。

| 建议类型 | 内容 |
|----------|------|
| 补充 | 增加 **产品定位一句话**（例：面向内网开发团队的、可私有化部署的工作流平台，强调 Ollama/MCP/命令行集成） |
| 补充 | 增加 **3～5 个用户故事**（谁、在什么场景、完成什么、得到什么收益） |
| 补充 | 增加 **成功指标**（如：工作流创建到首次成功执行 < 15 分钟、月活跃工作流数、平均执行成功率） |
| 修改 | 非目标第 4 条「单体架构」与 NFR-1「分布式部署」**二选一写清**：建议非目标改为「首期不支持多区域/多集群高可用」，NFR 改为「架构预留水平扩展能力」 |
| 删除/合并 | 「实时消息推送」与非目标表述易误解 — 建议改为「首期不提供站内信/邮件/短信告警，仅 Webhook 出站」 |

### 2.2 功能需求 FR-1～FR-8

**结论**：功能清单偏「能力目录」，缺少优先级、依赖关系与首期裁剪。

| FR | 评审要点 | 建议 |
|----|----------|------|
| FR-1 | 编辑器能力描述偏 UI 清单 | 补充：撤销/重做、复制粘贴、对齐/自动布局、无效连接校验、未保存离开提示 |
| FR-2 | 节点类型过多，一期难全做 | **必须**增加节点优先级表（P0 触发+HTTP+JSON+If+代码；P1 文件+DB；P2 SSH/WMI/MCP/Agent） |
| FR-2 | 「事件触发」「文件变化触发」边界不清 | 明确事件源（系统内/Webhook/OS 文件监听）及部署前提 |
| FR-3 | 「暂停」在开放问题中，正文已写支持暂停 | **统一**：首期仅支持「停止」，暂停/恢复列入 v1.1 |
| FR-3 | 「结果调试执行」未定义 | 补充：是否指「从某节点开始执行」「固定 Mock 输入」「单步调试」 |
| FR-4 | 继承规则在 AC-6，FR 未写优先级 | FR-4 正文补充：`工作流 > 用户 > 全局`，以及 `${VAR}` 引用语法 |
| FR-5 | 嵌套深度、循环调用未限制 | 补充：最大嵌套层数（建议 ≤5）、禁止循环引用检测 |
| FR-6 | 角色模型未定义 | 补充 RBAC 矩阵：至少 Owner / Editor / Viewer / Admin |
| FR-6 | 版本控制粒度不明 | 明确：自动保存 vs 手动发布版本；回滚是否影响正在运行的实例 |
| FR-7 | 模板市场运营未定义 | 首期建议仅「导入导出 + 内置 3～5 个官方模板」，市场放 P2 |
| FR-8 | 告警渠道未定义 | 与 NFR 对齐：首期仅 Webhook；邮件/钉钉后续版本 |

### 2.3 非功能需求

**结论**：指标偏口号，需可度量并与「非目标」对齐。

| NFR | 问题 | 修改建议 |
|-----|------|----------|
| NFR-1 | 「高并发」与约束「100 并发」矛盾 | 改为「支持不少于 100 个并发工作流实例；单实例队列排队策略可配置」 |
| NFR-1 | 「实时响应 < 1s」未定义场景 | 限定为「编辑器内操作反馈（拖拽、保存）P95 < 1s」，执行引擎单独指标 |
| NFR-1 | 「7x24 稳定」不可测 | 改为 SLA 目标或首期不做承诺，仅写「支持优雅停机与任务恢复」 |
| NFR-2 | 仅用户名密码不够 | 补充：Session 过期、API Key 作用域、审计日志（谁何时改了什么） |
| NFR-3 | 插件机制无接口约定 | 首期可写「内部节点注册 API」，对外插件 SDK 标为 P2 |

### 2.4 约束 / 假设 / 验收标准

| 项 | 问题 | 建议 |
|----|------|------|
| 约束 | 1000 节点/工作流对编辑器性能挑战大 | 建议首期上限 200，或标注「软限制 + 性能警告」 |
| 假设 | 「用户具备技术知识」与 UX 文档「快速上手」张力 | 区分「工作流编排」与「写代码节点」的能力要求 |
| AC | 缺少 FR-5 子工作流、FR-7 模板、FR-8 监控的 AC | 各补 1 条可程序化验收标准 |
| AC-1 | human-judgment 过多 | 拆分为可自动化项（节点数、连线合法性）+ 少量人工 UX 走查 |
| AC-3 | 「按顺序执行」不准确 | 改为「按 DAG 拓扑与分支逻辑执行」 |

### 2.5 开放问题 — 产品建议（供决策）

| 问题 | 建议决策 | 理由 |
|------|----------|------|
| 暂停和恢复 | **v1.1** | v1.0 停止即可；暂停涉及状态持久化与长任务，复杂度高 |
| 预估成本计算 | **Out of Scope v1** | 依赖多模型计费规则，非 MVP |
| 批量启动/停止 | **v1.0 P1** | 运维场景常见，实现成本相对可控 |
| 性能分析与优化建议 | **v2** | 需足够执行数据沉淀 |

## 三、建议修改清单（写入 spec.md v1.1）

以下为建议直接合入 PRD 的结构性增补（按优先级排序）：

### P0 — 阻塞设计与排期

1. 新增章节 **「MVP 范围（v1.0）」**：列出首期必做 FR、节点类型、明确不做项  
2. 统一 **单体 vs 分布式** 表述（见 2.1）  
3. 新增 **「安全与沙箱」** 小节：代码节点隔离、命令白名单、密钥不落日志、执行环境隔离  
4. 关闭或决策 **开放问题** 四项，并同步修正 FR-3 暂停描述  
5. FR-2 增加 **节点优先级表**

### P1 — 提升可交付质量

6. 概述增加 **用户故事 + 成功指标**  
7. FR-6 增加 **RBAC 权限矩阵**  
8. 补充 AC：子工作流、执行历史、导入导出冲突处理  
9. 增加 **「与 n8n 的差异」** 对比表（3～5 行即可）  
10. 增加 **「版本路线图」**：v1.0 / v1.1 / v2 功能锚点

### P2 — 商业化与运营预留

11. 多租户 / 工作空间（若面向团队）是否在 v1 支持  
12. 模板市场内容审核与版权  
13. 许可证与开源策略（若对标 n8n）
